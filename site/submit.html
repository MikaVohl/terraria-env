Submission kit

How to produce a Terraria-Lite result that can sit on the leaderboard: pick a version, evaluate on the right worlds, write one JSON file with every episode, and include tapes so the score can be replayed. Steps marked planned do not exist yet.

Versions

Results are only comparable within one version. State the version, and for v8 the knobs, in every result.

Evaluation commands

From the repository root. Build first with make -j4 all lib and uv sync --extra rl.

RL policy (v8, ore 300%, trees 200%)

Build the v8 library with the knobs used by the RL results, then evaluate a checkpoint on 128 worlds. The default package evaluator samples actions from the policy with a fixed sampler seed (--sample-seed, default 12345) under the legal-action mask.

make -C perf/v7 V7=$PWD/variants/v8 LIGHT_WINDOW=1 BUILD=build-v8-o3t2 \
  VARIANT="-DORE_PCT=300 -DTREE_HEIGHT_PCT=200"
TERRARIA_LITE_LIB=$PWD/perf/v7/build-v8-o3t2/libterraria.so \
  uv run python -m terraria_lite.ppo_eval ppo.pt --episodes 128 --seed-start 23000001

The v8 studies trained and evaluated through tools/iterate_ppo.py with --validation-seed-start 23000001 and --test-seed-start 25000001. Sources: README.md, variants/v8/README.md.

LLM harness rules

These are part of the evaluation contract. A different setting is a different track or scaffold, reported separately.

  • Action budget. 3,000 primitive actions per episode (v7 and v8), the same deadline as RL. Death ends the episode; no undo, reset or save-state search.
  • Calls. A fixed maximum of model calls per episode (256 in the Luna development config). A call-budget stop is reported as such, not as a 3,000-action completion.
  • Actions per call. Either one primitive action per call, or an open-loop list of up to 16 primitive actions with no conditional execution inside the list. The two interfaces are never pooled.
  • Illegal actions cost a tick. A known-illegal action is still an attempted action and uses one step.
  • Malformed output costs a noop. Batch validation is atomic: a partly invalid list does not run its valid prefix.
  • No tools. No code execution, shell, files, web search, full map, hidden state, navigation controller or strategic action mask. The model sees the RL observation, the legal-action mask and the public rules and recipes.
  • Notes and history. Model-authored notes are length-limited, history length is declared, and both reset every episode.
  • Cost guard and actual cost. A local dollar guard reserves conservative charges before each request from declared price ceilings. Report the provider-reported actual cost separately from the accounted (guard) cost; they can differ a lot.
  • Wall-clock cap. Declared per run and recorded; the world does not advance while the model thinks.
  • No retries, no fallbacks. No automatic retries, no silent fallback to another model or provider. A transport error stops the attempt and it is kept.
  • All attempts reported. Every world and replicate counts. No best-of-k, no dropped failures; infrastructure errors make the aggregate incomplete rather than shrinking the denominator.

Sources: docs/reports/LLM_EVALUATION.md, docs/reports/LLM_BENCHMARK_RESEARCH_2026_10.md.

Reporting rules

  • Every headline number comes with its interval and its sample size: IQM over training seeds with a bootstrap 95% CI (rliable definitions), the number of seeds and the number of worlds. LLM entries bootstrap over worlds.
  • All per-achievement success rates: 32 for v7 and v8, 38 for v9. Not only the headline.
  • Deaths (rate per episode) and first-unlock steps.
  • Budget and cost: environment steps and GPU-hours for RL; actions, calls, tokens, wall time and dollars for LLMs.
  • Prior knowledge in plain words (shaping, demonstrations, pretrained model, public rules).
  • A link to replayable tapes, so anyone can verify the episodes.

How these statistics are computed: methodology.

Verification

The simulator is deterministic, so a world seed and an action tape fix the whole episode. Verification replays the tape on the stated version and compares the recomputed steps, achievement mask, death and score with the reported ones. On the leaderboard an entry is marked:

  • replay: every episode's tape was replayed on the pinned build and matches the reported result. LLM runs also pass tools/eval_llm.py --mode verify, which checks the hash-chained event log state by state.
  • checkpoint: the trained checkpoint was re-evaluated on the same worlds with the same sampler seed and reproduced the score.
  • unverified: numbers reported without tapes or checkpoints. Shown, but marked.

A verifier that reads the results file directly, checks native_sha256, replays every listed tape and recomputes the aggregate is planned. Hash chains catch accidental changes; they do not prove anything against someone who rewrites every artifact, which is why hidden tests need independent administration.
