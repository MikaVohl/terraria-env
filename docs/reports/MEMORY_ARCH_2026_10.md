# Memory architectures for terraria-lite v7 (October 2026)

Branch `memory-arch` (on ScaleFF's `scale-ff` size knobs). Question: does general
learning capacity with *memory* (a recurrent core or a transformer over recent
steps) move PPO past the ~25/32 plateau on terraria-lite v7, where the policy
sees one 11x9 window and has no memory? No game knowledge was added: the memory
core only sees the encoder's own features.

Compact data: [`MEMORY_ARCH_2026_10.json`](MEMORY_ARCH_2026_10.json) (one row per
run: config, status, score curve with wall-clock, wall-achievement rates,
throughput, replay check, stockpiling diagnostics). Generated by
`tools/memory_report.py` from eg15 run directories.

## Answer in plain language

**No.** Neither memory nor its scale moves the wall, at equal environment
steps or at equal wall-clock.

- At equal steps the feed-forward control is ahead or level at every point.
  Solo 512M means (seeds 1901/1902): control **25.11**, LSTM-256 24.94,
  LSTM-256 with a 256-wide encoder 24.80, transformer-256 (128-step context)
  24.74, GRU-256 24.64 (1 seed), LSTM-512 24.71 (1 seed), LSTM-256 with a
  512-wide encoder 22.95 (1 seed). Feed-forward hidden-256 (the matched
  encoder without memory) 24.78. Memory learns *slower* early (64Mi: control
  22.27 vs LSTM 20.70, transformer 19.31) and only catches up to within
  ~0.2-0.4 by 512M.
- At 2B steps (seed 1901, matched schedules) the control ends at **25.39**
  (best 25.71) and LSTM-256 at 25.16 (best 25.30): the same plateau, still
  slightly behind.
- At equal wall-clock memory is far behind: alone on one MI350X the control
  trains at ~400k steps/s, the transformer at ~228k, LSTM-256 at ~137-159k,
  GRU-256 at ~95k. The control reaches 25.1 in 30 minutes; LSTM-256 needs 90
  minutes for 24.9 and 4.5 hours (2B) for 25.2.
- The never-earned crafts stay at exactly 0 in every one of the 19 completed
  runs and the 2B runs: iron pickaxe, gold pickaxe, iron chainmail, wood
  breastplate; return to surface 0-1%. Memory did not change ore finding or
  stockpiling: iron ore is collected in ~100% and iron smelted in 92-99% of
  worlds by every arm, but the iron-bar inventory peak stays at a median of 4-5
  (max 7-17; >=10 bars in 0-4 of 128 worlds), wood at a median of 12-16
  (never 30), gold bars at 1-2, and none of the big crafts was ever legal in
  any diagnostic episode (memory or not).

So the bottleneck is not that the policy forgets what it has seen in an 11x9
window: given a learned memory (recurrent or attention over 128 steps, up to
2.8M parameters) PPO converges to the same ~25/32 policy, which never builds
the 10-25-bar/30-wood stockpiles. Bigger memory/encoders did not help either
(LSTM-512 = LSTM-256; a 512-wide encoder is clearly worse at LR 3e-4).

## Implementation

`python/terraria_lite/memory_agent.py`, `MemoryActorCritic(memory, memory_size, memory_len, architecture, hidden, extra, depth=, cell_width=)`:

- Wraps the existing feed-forward encoder (`targets` by default, sized by
  `--hidden/--depth/--cell-width`). The encoder's global features `g`
  (width `hidden`) feed a memory core of width `--memory-size`; the existing
  heads (`TargetActor`, `GlobalCritic`, rebuilt for the wider input) read
  `cat(g, memory output, per-target context)`. The feed-forward path stays
  intact, so the core can only add information.
- `--memory gru|lstm`: one recurrent layer. Rollouts step it with an explicit
  cell using the `nn.GRU`/`nn.LSTM` weights (compile-friendly, same math as
  the fused kernel). The update replays each env's 128-step rollout from the
  stored rollout-start state (truncated BPTT over the rollout): all lanes'
  episode segments run as **one packed fused-RNN call** per minibatch (segments
  after an episode start begin from zeros), planned on the host from the
  `done` flags once per iteration so the update never waits on the device.
  A first version split the batch at every step where any lane reset; the
  packed replay made GRU 1.6x and LSTM 1.7x faster (54k -> 85k, 79k -> 131k sps).
- `--memory transformer`: 2 pre-LN causal self-attention layers (width
  `--memory-size`, 64-wide heads, 4x GELU MLP, zero-initialised residual
  output projections so the memory starts as a function of the current step)
  over the last `--memory-len` steps of the current episode. The only position
  signal is a learned per-head bias on the step offset. Rollouts keep a
  per-layer K/V ring buffer (all lanes write the same slot each step);
  episode boundaries are masks (offset <= steps since the episode started).
  The update recomputes K/V for the rollout's own steps and reuses the stored,
  detached K/V of the `memory_len - 1` steps before it (Transformer-XL style),
  so the first update pass reproduces the rollout exactly.
- State protocol shared with evaluation (`ppo_eval.evaluate`) and
  `tools/policy_diagnostics.py`: `initial_state(n, device)`,
  `core_step(x, state, done)`; the trainer adds `snapshot(state)`,
  `select(snapshot, lanes)`, `recur(encoded, snapshot, done, plan)`.
- Trainer (`ppo_agent.train`, `Config.memory/memory_size/memory_len`, CLI
  `--memory --memory-size --memory-len` in `ppo_agent` and
  `tools/iterate_ppo.py`): state carried across rollouts and reset at
  native-autoreset `done` flags; minibatches are whole env sequences
  (`envs/minibatches` = 64 lanes x 128 steps = the same 8,192 rows as the
  feed-forward minibatch); same PPO objective (`_ppo_loss` was split into the
  shared `_ppo_objective`, same ops). Works with compact obs, native autoreset,
  GPU collection, potential/novelty shaping, fused Adam, bf16 (encoder and
  heads under autocast, core in float32) and compile/compile-all (the rollout
  step and the transformer replay are compiled graphs; the packed fused RNN
  stays eager). Refuses options that touch agent internals (memory_features,
  SIL, aux loss, archive restarts, truncation bootstrap). Checkpoints carry the
  memory config; `load_agent` rebuilds them.
- `tools/explore_screen.py`: `mem_{gru|lstm}{size}[_h{hidden}]`,
  `mem_tf{size}l{len}[_h{hidden}]` arms on the `pot_e1024_max2` base, and
  `--pairs ARM:SEED` (explicit job lists; a job finished meanwhile is skipped
  instead of renamed).

## Verification

- Default training bit-identical (eg15, own GPU, branch library build-lw2):
  `perf/bench_trainer.py --envs 1024 --iters 6` -> `a18970ad67930ebb`, and with
  `--set native_autoreset=1 compact_obs=1 potential_mode=frontier novelty_coef=.01`
  -> `9b00de160bd6436b` (both as required; re-checked on the final code, see below).
- `tools/memory_checks.py` (CPU and eg15 GPU), all pass:
  - reset: a lane whose `done` is set continues exactly like a fresh state
    (GRU/LSTM error 0, transformer <2e-6);
  - replay: the update's sequence pass (packed RNN / batched attention from the
    snapshot) reproduces the step-by-step rollout outputs across episode starts,
    warm states and transformer windows shorter/longer than the rollout
    (max abs error 9e-8 RNN, 2.4e-6 transformer on CPU; <1e-6 / 2.4e-6 on GPU).
    Negative control: replaying from a zeroed snapshot gives errors 0.3-1.7, caught;
  - training from a deliberately sharp random policy: first-minibatch approx KL
    (ratio == 1 before any update) |KL| <= 7e-10 for all three cores; with a
    zeroed snapshot it is 1.2e-3, caught; checkpoint round trip through
    `load_agent`, `evaluate` and `policy_diagnostics.diagnose`.
- In the real 512M runs the logged first-minibatch KL stays 6e-6..5e-4: that
  is the bf16 update vs the float32 rollout (the feed-forward path has the same
  mismatch), not a replay error.

Re-check on the final trainer code (eg15 checkout at 3e7abd1, whose
`ppo_agent.py`/`memory_agent.py` equal the pushed head; HIP 4 alone after the
study): `a18970ad67930ebb` and `9b00de160bd6436b` again.

## The eg15 GPU-sharing incident

The first batch ran 2 processes per GPU (HIP 4-6). 6 of 10 runs died with
"Non-finite PPO loss" at 130-370M steps (all 4 transformer runs, 1 of 2
controls, 1 GRU), while Main's two 16B runs with the same flags (1 process per
GPU) ran past 2.7B. Findings (shared with ScaleFF/GpuShareBug):
`torch.multinomial` is calibrated (1.08e9 offline draws: 0 masked draws; draws
with p<1e-6: 7 observed vs 7.1 expected); on eg15 (ROCm 7.2.4) the
non-compiled float32 bench is bit-deterministic even on a shared GPU, but
`bf16=1` alone gives a different result every run; ScaleFF's in-situ traces
show grad-norm spikes up to 1e13 when shared and none in 346M steps alone.
Main switched both studies to 1 run per GPU. All conclusions below use the
**solo** runs; shared runs are kept in the JSON flagged `shared` (they are
spike-prone, and the dead ones end early), and shown only for completeness.

Ore finding (validation hit rates, solo runs at 512M): collect iron 98-100%,
smelt iron 92-99% (LSTM-256 h512: 61%), collect gold 87-98%, smelt gold
64-84% for every arm, memory or not; the control is at the top of each range.

collect and smelt enough for the 5-bar anvil (anvil 38-64% of worlds) and the
metal sword (6-14%) and then spend ~1,300-1,500 idle steps without another
achievement.
